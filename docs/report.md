# Отчёт по практике

Дата проверки: 15 ноября 2026 года.

## Выполненные работы

Подготовлены спецификация, девять пользовательских историй с критериями приёмки, функциональные и нефункциональные требования, процесс, ER-диаграмма, контракт API и backlog на 72 академических часа. Исходные требования прослеживаются до кода и автотестов через docs/test-plan.md.

Java-часть реализует создание, карточку, изменение описания/приоритета/срока, фильтры и пагинацию, справочник категорий, историю, валидацию и единые ошибки. Правила статусов централизованы в Status. Изменение статуса и история выполняются в общей транзакции с SELECT FOR UPDATE. Отдельная проверка подтверждает откат состояния при принудительной ошибке записи истории и защиту от двух одновременных одинаковых переходов.

Kotlin-часть используется работающим приложением: Java ReportController вызывает ReportService, который получает одну выборку через Java ReportSource. Все метрики используют заявки, созданные в [from,to). Отчёт содержит нулевые значения отсутствующих статусов и приоритетов, открытую просрочку и среднее время только для RESOLVED.

Созданы Flyway-миграции, демонстрационный генератор через API, OpenAPI и Postman-коллекция с проверками ответов. Dockerfile использует две стадии и непривилегированного пользователя. Compose обеспечивает именованный том, readiness БД и приложения, переменные окружения и stdout-логи. Подготовлены резервное копирование, восстановление, deploy, ручной и автоматический rollback.

Разработка велась с тематическими ветками и merge-коммитами. Изменения CI/CD и второго релиза оформлены pull request №1 и №2. Ссылки приведены в docs/submission.md.

## Два решения, связанные с Kotlin

1. `SummaryReport` — data class, а `averageResolutionSeconds` имеет тип `Double?`. Отсутствие завершённых заявок выражается null, а не NaN или условным нулём. Для Java nullable closedAt безопасно обрабатывается через `?.let`, `mapNotNull` и `takeIf`. Kotlin-тест отдельно проверяет отсутствие close time на границе Java-интерфейса, даже несмотря на ограничение целостности в PostgreSQL.
2. Распределения строятся через `groupingBy().eachCount()`, затем `Status.entries.associateWith` и `Priority.entries.associateWith` дополняют отсутствующие значения нулями. Длительности вычисляются через `filter`, `mapNotNull` и `average` из той же единственной выборки. Это сохраняет проверяемую общую базу для всех метрик без отдельных SQL-запросов на каждый показатель.

Восемь тестов написаны на Kotlin. Среди них есть вызов Java TicketService с проверкой запрета открытия завершённой заявки и проверка Java Ticket на точной границе срока.

## Проверка контейнеров и эксплуатации

Контейнерный сервис запущен с PostgreSQL 17.6 и Java 21.0.9. Обе миграции применены автоматически. Readiness возвращает UP. Сквозной smoke выполняет успешный сценарий и отклонённые изменения терминальной заявки.

На учебном стенде Kali Linux проверена сохранность после `docker compose down` и `up` без удаления тома. Резервная копия pg_dump восстановлена в отдельную базу, содержимое categories, tickets и status_history совпало. Протокол: evidence/kali-verification.json.

Проверен откат релиза practice-2 к первому образу. После возврата сохранилась заявка id=4, два smoke-сценария завершились PASS, приложение и PostgreSQL остались healthy. Между релизами схема БД не менялась. Для будущих релизов совместимость миграций требуется проверять отдельно.

Контрольная сборка с неуспешным health check также подтвердила автоматический возврат к рабочему образу и ненулевой код завершения deploy. Протокол: evidence/automatic-rollback.json.

## CI/CD

Настроен GitHub Actions: проверки Java/Kotlin, сборка и тесты, публикация отчётов, сборка/публикация образа с тегом SHA, доставка на self-hosted runner и проверка работоспособности. Для PR выполняются проверки без публикации и развёртывания. Ошибка verify блокирует последующие jobs через needs.

Два полных pipeline завершились success для verify, publish и deploy. Образы опубликованы в GHCR с тегами SHA и запущены через self-hosted runner на Kali Linux в VirtualBox. Подтверждены healthy обоих контейнеров, readiness UP и smoke PASS. На стенде отдельно прошли 56 тестов на Java 21 и проверка backup/restore. Идентификаторы двух образов, ссылки на pipeline и результаты отката приведены в docs/submission.md и evidence/kali-verification.json.

При первой доставке остановка runner прервала выгрузку отчёта; повтор job завершился успешно. При публикации второго релиза Maven Central вернул HTTP 429; повтор упавших этапов завершился успешно.

## Трудозатраты и ограничения

План: анализ 6, проектирование 6, Java 18, Kotlin 10, тестирование 12, эксплуатация 8, CI/CD 8, документация и защита 4 — всего 72 академических часа. Фактические трудозатраты учитываются в журнале практики; приведённые значения являются плановыми оценками.

Решение не содержит аутентификацию, клиентский интерфейс, распределение исполнителей, уведомления и вложения. Оно предназначено для учебного стенда. По умолчанию опубликован только loopback-порт гостевой ОС. PostgreSQL-порт наружу не публикуется, за исключением явно выбранного режима разработки. Показатели отчёта отражают текущее состояние выбранных по createdAt заявок, а не исторический снимок на конец периода.
