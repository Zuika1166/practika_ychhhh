# Защита: сценарий на 10–15 минут

## Подготовка до начала выступления

Обновить документы в клонированном репозитории:

```bash
cd ~/practika_ychhhh
git pull --ff-only
```

Заранее выполнить полный прогон тестов на Java 21 и открыть готовые отчёты. На выступлении достаточно показать результаты и выбранный тест.

```bash
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
./gradlew --no-daemon spotlessCheck build
firefox build/reports/tests/test/index.html
firefox build/reports/jacoco/test/html/index.html
```

На стенде сейчас подтверждён первый образ после отката. Чтобы на защите показать реальное возвращение второй версии к первой, заранее включить уже скачанную вторую версию:

```bash
cd /opt/helpdesk
bash scripts/deploy.sh ghcr.io/zuika1166/practika_ychhhh:60a2ce4259cedce23de43eae00e409c6b3b4e04b
curl --fail http://127.0.0.1:8080/actuator/info
```

Ожидается release=practice-2. Команда использует ранее опубликованный образ и создаёт проверочную заявку. Если образ удалён локально, для скачивания приватного пакета потребуется вход в GHCR; оба образа лучше сохранить на ВМ после проверенных доставок.

Заранее открыть вкладки:

- Swagger: http://127.0.0.1:8080/swagger-ui/index.html
- docs/specification.md, требование F-04.
- Status.java и TicketService.java.
- ApiIntegrationTest.java, метод e2eForbiddenOperationLeavesAllDataUnchanged.

- Успешный pipeline: https://github.com/Zuika1166/practika_ychhhh/actions/runs/43756431655
- Отчёты JUnit и JaCoCo.

Терминал для демонстрации команд открыть в /opt/helpdesk. Исходники и отчёты сборки находятся в ~/practika_ychhhh. Runner при необходимости запустить в его отдельном терминале. Фактические трудозатраты заполнить по собственному журналу.

## 0:00–0:40. Кратко представить проект

«Это серверный сервис обработки заявок технической поддержки. Он регистрирует заявки, контролирует переходы статусов, хранит историю, поддерживает поиск и рассчитывает статистику. Основная часть написана на Java и Spring Boot, статистика — на Kotlin. Данные хранятся в PostgreSQL. Для демонстрации REST API использую Swagger UI».

## 0:40–2:20. Связать требование, код и тест

Открыть docs/specification.md, F-04: RESOLVED и CANCELLED — терминальные статусы; повторное открытие запрещено.

Показать src/main/java/ru/practice/helpdesk/Status.java, метод allows: разрешены только NEW→IN_PROGRESS, IN_PROGRESS→RESOLVED и отмена из двух открытых статусов.

Показать TicketService.changeStatus: загрузка и блокировка строки, проверка allows, ошибка 409 до записи при запрещённом переходе, изменение статуса и сохранение истории в @Transactional.

Показать src/test/java/ru/practice/helpdesk/ApiIntegrationTest.java, метод e2eForbiddenOperationLeavesAllDataUnchanged. Он создаёт и завершает заявку, сохраняет карточку и историю, пытается открыть и отредактировать её, проверяет 409 и полное совпадение данных после отказа. В готовом отчёте показать, что тест прошёл.

«Таким образом, требование зафиксировано в спецификации, реализовано в сервисе и проверено через HTTP с настоящей PostgreSQL. Дополнительно параметризованный enforcesEveryTransition проверяет все 16 пар статусов».

## 2:20–5:20. Создать заявку, сменить статус, получить отчёт

В Swagger нажимать Try it out, заполнять параметры и нажимать Execute. Смотреть фактический Server response.

1. GET /api/categories. Получить существующий categoryId; в текущем справочнике Оборудование имеет id=1.
2. POST /api/tickets. Тело:

```json
{"title":"Проверка принтера на защите","description":"Принтер не печатает","categoryId":1,"priority":"HIGH","dueAt":"2030-01-20T16:00:00Z"}
```

Показать HTTP 201, Location, присвоенный id и статус NEW. Записать полученный id и подставлять его далее. При демонстрации после указанной даты выбрать будущий dueAt.

3. PATCH /api/tickets/{id}/status. Передать:

```json
{"status":"IN_PROGRESS"}
```

Показать 200 и IN_PROGRESS. Затем тем же методом:

```json
{"status":"RESOLVED"}
```

Показать 200, RESOLVED и заполненный closedAt.

4. GET /api/tickets/{id}/history. Показать три записи: создание, начало работы, завершение.
5. GET /api/reports/summary. Параметры from=2020-01-01T00:00:00Z, to=2100-01-01T00:00:00Z.

«Все показатели используют одну выборку заявок, созданных в интервале [from,to). Распределения отражают текущие статусы и приоритеты. Просрочка считается на момент запроса. Среднее время решения в секундах считается только для RESOLVED; при отсутствии таких заявок возвращается null».

На стенде уже есть другие заявки, поэтому createdCount и RESOLVED могут быть больше единицы. При пустой выборке все счётчики нулевые, среднее null. Для отдельной проверки пустой выборки можно выбрать период 2000-01-01T00:00:00Z — 2000-01-02T00:00:00Z, если в нём нет данных.

## 5:20–7:10. Объяснить взаимодействие Java и Kotlin

Показать цепочку:

```text
HTTP GET /api/reports/summary
→ ReportController.java
→ ReportService.kt
→ ReportSource.java
→ TicketRepository.java / JdbcTemplate
→ PostgreSQL
```

«Spring внедряет Kotlin-сервис в Java-контроллер через конструктор. Kotlin-сервис использует Java-интерфейс ReportSource, реализованный JDBC-репозиторием. Java и Kotlin компилируются для JVM 21 и работают в одном приложении, поэтому отдельный сетевой вызов между языками не нужен».

Показать SummaryReport и summary в ReportService.kt:

- data class описывает модель отчёта и автоматически предоставляет методы работы с данными.
- Double? позволяет вернуть null для отсутствующего среднего.
- ?.let безопасно обрабатывает отсутствующий closedAt.
- groupingBy().eachCount() считает распределения.
- associateWith дополняет отсутствующие статусы и приоритеты нулями.
- filter, mapNotNull и average вычисляют среднее только по завершённым заявкам.

«Kotlin реализует работающую бизнес-функцию. Восемь тестов написаны на Kotlin; kotlinInvokesJavaServiceAndEnforcesTerminalStatus проверяет Java TicketService».

## 7:10–8:20. Показать отклонение запрещённой операции

Для только что завершённой заявки повторить PATCH с IN_PROGRESS. Ожидается HTTP 409 и code=INVALID_TRANSITION.

Повторно вызвать GET карточки и GET истории. Показать, что статус остался RESOLVED, closedAt сохранился и четвёртой записи истории не появилось.

«Запрос корректен по форме, но конфликтует с текущим состоянием заявки. Поэтому возвращается 409. Сервис проверяет переход до изменения данных».

Если спросят про редактирование, PUT закрытой заявки с description, priority и dueAt также вернёт 409.

## 10:10–11:40. Объяснить диагностику

«Сначала проверяю состояние контейнеров, затем логи нужного сервиса, затем readiness и конфигурацию соединения».

```bash
docker compose ps
docker compose logs --tail=100 app db
curl -i http://127.0.0.1:8080/actuator/health/readiness
```

БД недоступна: проверить состояние и логи db, pg_isready, DB_URL, пользователя и согласованность пароля. Изменение .env не меняет пароль существующего PostgreSQL-тома.

Health check не проходит: проверить логи app, запуск Java, доступ к БД, память и правильность порта. Readiness зависит от состояния БД; 503 означает неготовность сервиса.

Ошибка Flyway: прочитать ошибку в логах и проверить flyway_schema_history. Применённые миграции восстанавливать в исходном виде, исправления схемы оформлять новой миграцией. Перед ручной коррекцией сделать backup и проверить изменения на отдельной восстановленной базе.

Рабочие данные при диагностике сохранять. Удаление тома не является способом исправления ошибки миграции или пароля.

```bash
bash scripts/rollback.sh ghcr.io/zuika1166/practika_ychhhh:9eb5ae4585c0965e3387c79b7f47836b89136ac2

```

Показать возвращение SHA 9eb5ae4…, отсутствие release=practice-2, сохранение заявки №4 и healthy. Скрипт отката сам выполняет smoke, результат должен быть PASS.

«Возвращается предыдущий контейнерный образ, а том PostgreSQL сохраняется. Вторая версия меняет метку релиза и не меняет схему БД. В дальнейшем миграции должны сохранять совместимость с предыдущим приложением. Восстановление резервной копии — отдельная операция, она не является автоматической частью возврата образа».
